0Reactの描画と購読の仕組み 基礎

本編のあちこちで前提になる React の仕組みを、ここにまとめています。本編を読んでいて「なぜそうなるのか」が分からなくなったら、この章に戻ってきてください。補正ログ Q1〜Q7 で解消した疑問の結論も、ほぼすべてこの章に集約されています。

0-1マウント・再レンダリング・アンマウント

コンポーネントには3つの段階があります。「再レンダリング（再描画）」と「マウントし直し（作り直し）」は別物です。

段階何が起きるかuseState の値
マウント（作成）初めて画面に出る。関数が実行される初期値で作られる
再レンダリング（再描画）関数がもう一度最初から実行される前回の値が保持される
アンマウント（破棄）画面から消える捨てられる

Java にたとえると次のとおりです。

  • コンポーネントのインスタンス ＝ オブジェクト
  • useState の値 ＝ そのオブジェクトのフィールド
  • 関数本体 ＝ 描画のたびに呼ばれるメソッド
  • const location = useLocation() などの変数 ＝ メソッドのローカル変数

再レンダリングは「同じオブジェクトのメソッドをもう一度呼ぶ」ことです。ローカル変数は毎回作り直され、フィールドは残ります。

遷移の例再レンダリングマウントし直し
/employees/1 → /employees/2（パスパラメータだけ変化）されるされない
/employees → /employees?dept=dev（クエリだけ変化）されるされない
/employees/1 → /employees/new（別ルートへ）—Detail は破棄、New が新規作成
上記すべての EmployeesLayoutされるされない

0-21回の描画サイクル

useEffect は「描画が終わった後に呼んでもらうコールバック」を登録する仕組みです。中身が実行されるタイミングは依存配列で決まります。

  • マウント後（初回の③）… 必ず実行
  • 2回目以降の③ … 依存配列の値が前回から変わっていれば実行

0-3useState の初期値はマウント時にしか使われない

React 公式ドキュメントの useState リファレンスにも「初期値の引数は最初の描画の後は無視される」と書かれていますが、入門記事ではあまり強調されません。このノートで何度も効いてくる性質です。

  • 落とし穴になる例：4-7 同じコンポーネントは作り直されない（社員1のメモが社員2に残る）
  • 利用している例：6 の EmployeeNew（state を初期値に入れる）、7-7 完了メッセージの保持（setter なしの useState で値を固定）

引数は無視されますが、評価（計算）は毎回行われています。重い計算は関数で渡すとマウント時だけ実行されます。

0-4再レンダリングが起きる3つの原因

  1. 自分の useState の値が setXxx で変わった
  2. 購読しているコンテキストの値が変わった（useLocation・useParams・useSearchParams はこれ）
  3. 親コンポーネントが再レンダリングされた
決定的なポイントuseEffect はこの3つに含まれません。「描画の後で何かを実行する場所」であって、それ自体が描画を起こすわけではありません。useEffect の中で setXxx や navigate() を呼んだときに、その呼び出しが 1 や 2 を起こします。（Q4 で確立）

0-5location が届く仕組み（BrowserRouter の中身）

React Router も特別な仕組みではなく、普通の useState とコンテキストの組み合わせで作られています。

ブラウザの履歴を書き換えるだけでは React は気づきません。setLocation（＝ useState のセッター）があるから再レンダリングが起きます。補正ログに出てくる「内部的には setState」という表現は、このことを指しています。

再レンダリングが起きるには2つが揃う必要があります。

  • きっかけ：location が変わる（setLocation）。変わらなければ、useLocation を呼んでいても何も起きない。
  • 届け先：useLocation() で購読している。変わっても、購読していないコンポーネントには届かない。

useNavigate() も描画のたびに呼ばれますが、新しく作っているのではなく、React Router が保管している関数を受け取っています（Spring で言えば DI コンテナからシングルトンの Bean を取得するイメージ）。では useLocation() も同じなのか、という違いは 0-8 navigate と location の違い にまとめています。

0-6「state」と名のつく4つのもの

名前どこのもの正体
history.pushState() / replaceState()ブラウザ標準履歴エントリを追加／置き換えるメソッド。React とは無関係
history.stateブラウザ標準各履歴エントリに付けられる「荷物」
location.stateReact Router上の荷物を React Router 経由で読んだもの（6 で使用）
useState / setXxxReactコンポーネントの状態。setState はセッターの総称的な呼び名

例/employees/2?dept=devURLに出ない
意味どのリソースかどう表示するか一時的な受け渡し
ルート定義path: ":id" が必要不要不要

選び方の基準は「URLを共有・リロードしたときに再現されるべき情報か」です。

0-8navigate と location の違い：「変数」と「中に入る物」を分けて考える

const navigate = useNavigate() も const location = useLocation() も、関数本体に書かれているので描画のたびに実行されます。ここで「変数（入れ物）」と「その変数が指す物（オブジェクト）」を分けて考えると、両者の違いがはっきりします。

  • 変数は、どちらも描画のたびに新しく作られるローカル変数です（0-1）。
  • 中に入る物が違います。navigate にはいつも同じ関数が入り、location には URL が変わるたびに新しいオブジェクトが入ります。
const navigate = useNavigate()const location = useLocation()
変数（入れ物）描画のたびに新しいローカル変数描画のたびに新しいローカル変数
中に入る物React Router が保管している移動用の関数React Router が持っている「現在の location」オブジェクト
URL が変わらない再描画（自分の useState の更新など）同じ関数同じオブジェクト
URL・state が変わったとき基本は同じ関数（BrowserRouter 方式ではパスが変わると作り直されることがある）新しいオブジェクトに差し替わる（古いオブジェクトは書き換えない）
Spring のたとえシングルトンの Bean。何度取得しても同じインスタンス状態が変わるたびに作り直される不変の値オブジェクト（DTO）。中身を書き換えず、新しい物と取り替える

この違いが、7-7 の依存配列 [location, navigate] の意味にもつながります。依存配列は「前回と同じ物か」を比べるので、毎回同じ navigate は useEffect の再実行を起こさず、URL が変わって差し替わった location だけが再実行を起こします。

1基本的なページ遷移 本編

目標：/ と /about の2ページを切り替える。

1-1何が起きているのか

React Router の役割は、「今のURL」を見て「どのコンポーネントを表示するか」を決めることです。Spring では DispatcherServlet と HandlerMapping がサーバー側でしていた仕事を、ブラウザ側で行っています。

1-2部品と役割

部品役割Spring のイメージ
<BrowserRouter>URLの変化を監視し、現在のURLを配下に配るDispatcherServlet
<Routes>現在のURLと各 Route を照合し、一致した1つを選ぶHandlerMapping
<Route path element>「このパスならこのコンポーネント」の1行@GetMapping
<Link to>リロードせずにURLを書き換えるリンク<a th:href>

1-3コード

BrowserRouter の外では Link や useParams などは使えません。「現在のURL」は BrowserRouter が配る仕組み（0-5）だからです。

各ページは見出しを1行出すだけのコンポーネントです。

1-4動きを追う

ポイントは手順6です。<Routes> の外側は作り直されず、中身だけが入れ替わります。この原理は 2-4 で1段内側でも同じように働きます。

1-5なぜ <a href> ではダメなのか

<a href="/about"><Link to="/about">
サーバーへのリクエスト発生する発生しない
JSの状態（useStateの値など）すべて消える保たれる
画面白くなってから再表示一瞬で切り替わる

<Link> も HTML としては <a href> として出力されるので、「新しいタブで開く」も動きます。普通のクリックのときだけ JS が割り込んでリロードを止めています。

1-6パス照合のルール（v6以降）

  • 完全一致が基本。path="/" は /about に一致しない。v5 の exact は不要。
  • 記述順は関係ない。最も具体的なものが選ばれる（4-5 で詳しく）。
  • * はどのパスにも一致するので404用。
実務でハマりやすい点：直接アクセス時の404開発サーバーでは /about を直接開けても、静的配信だけのサーバー（Nginx など）では404になることがあります。サーバーに about というファイルは無いからです。どのパスでも index.html を返す設定（フォールバック）を入れれば、React Router が起動してURLを解釈します。

2ネストされたページ遷移 本編

目標：/employees（一覧）と /employees/new（登録）に、共通の見出しとサブメニューを1か所で書く。

2-2考え方：URLの階層 ＝ 画面の入れ子

  • パスの組み立ては、クラスの @RequestMapping("/employees") ＋ メソッドの @GetMapping("/new") と同じ発想。
  • 画面の組み立ては、Thymeleaf Layout Dialect の layout:decorate ／ layout:fragment に相当。

2-3コード

子として <Outlet /> の位置に入る2つのページと、一覧が使う仮データです。

2-4動きを追う（/employees/new）

  1. 親 path="/employees" が先頭部分に一致 → 残りは "new"
  2. 子を照合：index は残りが空のときだけ一致 → ✕、path="new" → ✔
  3. EmployeesLayout を描画し、その <Outlet /> の位置に EmployeeNew を描画

一覧 ⇄ 新規登録 を移動しても EmployeesLayout はマウントし直されず、<Outlet /> の中だけが差し替わります（1-4 と同じ原理が1段内側で起きている）。

2-5重要な3要素

  • <Outlet />：子の描画位置。書き忘れると子は何も表示されず、エラーも出ない。
  • index：親のパスちょうどで表示する子。path と同時に書けず、子も持てない。
  • 子の path は相対：/ を付けずに書くと親と連結される。

2-6Link も相対パスで書ける

<Link to="new"> は、そのリンクが置かれたルート（/employees）を基準に /employees/new になります。URL を変更しても Link を直さずに済むのが利点です。

2-7応用：path のないレイアウトルート

RootLayout の中身は、header と <Outlet /> だけです。

3ルート定義の分割 本編

目標：App.jsx は「どの機能をどのURLに置くか」だけにし、社員管理の中のルートは別ファイルに任せる。Spring で Controller を機能ごとに分けるのと同じ。

(a) 子コンポーネントが <Routes> を持つ(b) オブジェクトで定義して組み立てる
書き方JSX（これまでと同じ）JavaScript の配列・オブジェクト
App は子ルートを知っているか知らない（丸投げ）知っている（1本の木）
/*必要不要
createBrowserRouter との相性△◎

3-2(a) 子コンポーネントが <Routes> を持つ

  • /* は「/employees で始まるURLはすべて受け持ち、残りは中の Routes に任せる」という意味。付け忘れると /employees/new が NotFound になる。
  • /employees/xxx は App 側の /employees/* に先に一致するので、App 側の * には届かない。中にも404を書く。

3-3(b) ルートをオブジェクトで定義する

<Route> の正体は「URLと画面の対応表」という設定データです。最初からオブジェクトで書けば、普通の値として別ファイルに分け、export / import で組み立てられます。このノートでは以降(b)で進めます。

まず社員管理側です。2 で <Route> の入れ子として書いた内容を、そのままオブジェクトに書き直して export します。親の element は 2-3 の EmployeesLayout（<Outlet /> を持つ枠）で、children の各要素がその <Outlet /> に入ります。

次に App 側で、この employeeRoutes を配列に組み込みます。useRoutes に配列を渡すと、<Routes> と同じように一致した画面を返します。

(b)は親子が children で1本の木になるので /* は不要で、/employees/xxx は App 側の * に届きます。

3-4発展：createBrowserRouter

v6.4 以降（v7含む）の推奨方式で、(b)と同じオブジェクト形式です。loader などの追加機能が使えます。

紛らわしい話題React.lazy の「コード分割（code splitting）」は、読み込むJSファイルを分けて表示を速くする別の話です。

4-5new と :id はぶつからないのか

Spring で @GetMapping("/new") と @GetMapping("/{id}") を併記したときに固定パスが優先されるのと同じです。

4-6値は常に文字列

変換を忘れると「データはあるのに見つからない」バグになり、エラーも出ません。URL は利用者が書き換えられるので、/employees/999 や /employees/abc が来る前提で受け取る側で対処します（7-5 で自動的に一覧へ戻す形に変えます）。

4-7同じコンポーネントは作り直されない

訂正済み最初の説明では「作り直さず、使い回します」と書いていました。この表現は、「再描画もされない」と読める曖昧な書き方でした。正しくは「再レンダリングはされるが、マウントし直されない」です。→ Q2 ／ 訂正一覧 F1

id や employee は毎回計算し直されるので正しく切り替わります。問題になるのは useState の値だけです（理由は 0-3 初期値はマウント時にしか使われない）。対処法は2つ。

5クエリパラメータ 本編

目標：一覧を ?dept=dev&order=desc で絞り込み・並び替えする。セレクトボックス操作 → URLが変わる → 一覧が変わる。

5-2クエリはルート照合に関係しない

/employees?dept=dev は /employees と同じルートに一致します。ルート定義は一切変更しません。

5-3useSearchParams の基本

保存場所がURLになった useState と考えると分かりやすいです。searchParams の正体はブラウザ標準の URLSearchParams です。

5-4コード

EmployeeList の最終版は完成コードにあります（絞り込み部分が5の内容）。画面の状態を useState では持たず、セレクトボックスの表示も一覧の中身も、URL だけを情報源にして毎回計算しています。

5-5動きを追う

関連する補正「クエリが変わったら本当に再描画されるのか？」という疑問は Q1、「再描画」と「作り直し」の区別は Q2 で解消しています。

  • 値は文字列か null。デフォルト値（??）と型変換は自分で行う。
  • setSearchParams はクエリ全体を置き換える。

「変数」と「中に入る物」を分けると整理できる。変数はどちらも描画のたびに作り直されるローカル変数で、ここは同じ。違うのは中に入る物で、navigate には毎回同じ関数が入る。location には、URL が変わらない間は同じオブジェクトが入り、URL が変わると新しいオブジェクトに差し替わる。Q1 の「毎回作り直される」は変数の話で、オブジェクトまで毎回新しくなるという意味ではなかった。

Spring にたとえると、navigate は「シングルトンの Bean」、location は「状態が変わるたびに作り直される不変の値オブジェクト（DTO）」です。
